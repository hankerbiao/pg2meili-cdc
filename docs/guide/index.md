# 开发指南概览

UniData 提供“单写多搜”的数据同步与搜索能力。这里汇总了你需要了解的核心概念与阅读路径。

![系统架构图](/images/主要架构图.png)

## 1.1 设计思路

- **写入集中**：业务只写主库，避免双写逻辑。
- **同步自动化**：通过 CDC 捕获变更，推送到搜索侧。
- **就近检索**：查询流量落到最近的搜索节点。

## 1.2 核心价值

- **解耦**：写入与搜索独立扩展，互不阻塞。
- **可观测**：数据库 → Kafka → 搜索引擎链路清晰。
- **可伸缩**：多地部署与扩容更易管理。

## 1.3 原理概述

UniData 以数据库日志为唯一可信数据源：写入只落 PostgreSQL，CDC 捕获变更并写入 Kafka，消费者按顺序处理消息并构建搜索索引。这样既避免业务双写，又具备可回放与补偿能力。

## 1.4 作为数据浏览器的适用性

适合：

- 需要在多地域快速检索、浏览业务文档的场景（就近访问、低延迟）。
- 数据写入频繁但查询以文本检索为主的场景（需求/测试用例/知识库）。
- 希望将读写解耦、降低业务侧检索复杂度的场景。

不适合：

- 强一致读（必须“写入即刻可检索”）的业务流程。
- 不允许 CDC 异步同步延迟、或需要严格秒级一致性 SLA 的场景。

## 1.5 方案对比

| 维度 | 直接对接搜索引擎 | **UniData + CDC 架构** |
| :--- | :--- | :--- |
| 一致性模型 | 业务侧双写，易出现漂移 | 变更捕获，最终一致 |
| 写入路径 | 写入与索引紧耦合 | 写入与索引解耦 |
| 回放/补偿 | 需业务自实现 | 基于日志可回放 |
| 多地域同步 | 需自研 | 架构内建 |
| 延迟特性 | 取决于链路与部署 | 就近检索，延迟可控 |
| 故障隔离 | 搜索故障可能影响写入 | 写入与搜索互相隔离 |
| 可观测性 | 依赖业务埋点 | 链路清晰、便于定位 |
| 运维复杂度 | 低 | 中高（Kafka/Debezium） |
| 适用场景 | 小规模/单地域 | 多地域/高可用 |
